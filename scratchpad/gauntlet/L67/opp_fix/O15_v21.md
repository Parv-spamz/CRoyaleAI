## R4 singleton_resight -- design

For a base with `BODIES.get(base)` absent or <= 1 ("singleton"), a NEW track (one that did not match any
existing live track by the normal proximity rule) is suppressed (created, not charged) if the MINIMUM gap
between `now` and any existing same-base track's last-seen time is:
- <= 0.5s (hardcoded `SINGLETON_DOUBLE_WINDOW_S`, documented in V2_PARAMS, not a constructor kwarg per
  ticket's own kwarg list): genuine double (both alive, simultaneous) -- do NOT suppress, charge normally.
- else <= `singleton_window_s` (4.0 default): re-sighting -- suppress (no charge).
- else (or no existing track at all): normal charging.

Implemented as `_singleton_resighted(base, now)`, folded into the existing per-cluster suppression loop
(`suppressed[i] = spawn_suppressed OR singleton_resighted`), read-only against `self._tracks` exactly as R1
already does (checked before any of this update's own new tracks are appended, so same-update simultaneous
plays never see each other and are unaffected -- consistent with the "two miners 0.3s apart" test crossing
TWO update() calls, not one).

## R5 lifetime_absorb -- design

Replaces `_charge_groups`'s time-window (`body_group_window_s`) + single-centroid-per-base matching with:
persistent multi-group state per base (`self._deploy_groups: dict[str, list[{id, cap}]]`), tracks tagged
`tr["group_id"]` on creation. A group's "live members" = the CURRENT COUNT OF DISTINCT TRACK OBJECTS in
`self._tracks` carrying its id (garbage-collects itself for free via the existing `forget_s` expiry --
no separate liveness bookkeeping). A new cluster point joins the first group (for its base) that (a) has
fewer than `cap` (`ceil(n/BODIES[base]) * BODIES[base]`, same formula as before) live track-members, AND
(b) lies within `r_body` of ANY of that group's live member positions (not just a stored centroid -- this is
the literal fix for the measured over-billing: a body drifting/re-detected far from the group's original
centroid but still near one of its actual living neighbours). No qualifying group -> starts a new deployment
(new id, new cap, charged `ceil(n/cap)` same as before). `body_group_window_s`/legacy per-base single-dict
state (`self._body_groups`) is UNCHANGED and still used verbatim when `lifetime_absorb=False` (ablation-off
parity with pre-O15 V2).

Test construction note (my own choice, hand-computed against my own implementation, matching the ticket's
required OUTCOMES): "live member" is counted as track-object count, not detection count -- so the drift test
deploys the initial 5 bodies as **more than one** track object (a chained arc, each pair > cluster_radius
apart) rather than one merged blob, giving headroom under the object-count cap for the drift case to land as
a genuinely NEW track that still finds room in the group; the "6th body" test deploys the initial 5 as five
mutually-far track objects so the group is already at its 5-object cap before the 6th arrives. Both are
faithful to the ticket's literal English ("member tracks" = track objects) and both required outcomes are
reproduced. Flagged as a judgment call in how "5 barbarians deployed" is laid out spatially, not a deviation
from the ticket's stated pass/fail requirement for either scenario.

Verifier: PASS_WITH_NOTES; all attempt-3 cases (a)-(j) held. One remaining MEDIUM, fixed here.

**FIX (MEDIUM, within-one-update ordering)** -- `_charge_groups_lifetime`'s `active_n` is computed from
`self._tracks` (via `_group_live_members`/`matched_n`), which does not gain a new entry for a point until
AFTER the whole function returns (tracks are appended later, in `update()`'s own loop). So two same-base
points landing near ONE group in a SINGLE sample were each checked against the group's identical, unchanged
`active_n` -- both could independently "fit" a budget that in reality only had room for one of them.

Fix: a `pending: dict[int, int]` local to each `_charge_groups_lifetime` call now accumulates the body count
already committed to a group by an EARLIER point in the SAME `points` list; the join test becomes
`active_n(g) + pending.get(g["id"], 0) + n <= cap`, and a successful join adds `n` to `pending[g["id"]]`
immediately. This makes the result independent of iteration order: whichever point is evaluated first claims
the remaining budget via `pending`, and any later point sees that claim and is blocked once there is no room
